### Phase 1 RULE SCAN
Based on the task description and "orientation story" analysis, here are the rules that change state during the event or claim list:

1.  **Grant Rule**: Requests arrive in strict order; if the pool covers the full ask, grant the full amount and subtract from the pool. If the pool cannot cover the full ask, grant the partial available amount (pool drops to zero) and mark the request as partially granted.
2.  **Denial Rule**: A request arriving at an empty pool is denied (listed by ID). The state does not change for this specific event other than recording the denial; no tokens are added back immediately.
3.  **Expiry/Return Rule**: When a grant expires (triggered by the completion of the *next* request), it returns half of the amount actually granted to that specific grant, rounded down (`floor(granted / 2)`). This return is applied to the pool *before* the next request is processed.
4.  **No-Other-Return Rule**: Grants never return any other way (e.g., no automatic refunds upon denial or partials unless explicitly expired).

**Triggers:**
*   Request Arrival ($r_1$ through $r_6$) triggers Grant/Denial logic.
*   Completion of Request $r_{n}$ triggers Expiry/Return for the grant associated with $r_{n-1}$.
