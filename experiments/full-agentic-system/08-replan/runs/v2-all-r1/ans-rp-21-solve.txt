### Phase 1: Rule List Analysis
We identify the rules governing state changes (loads, evictions, deferrals) as described in the text. The order of application follows the "higher in the list" rule mentioned in the discipline section.

1.  **Load Arrival & Fit Check**: When a load arrives, check if it fits in available space (`capacity - current_loads`).
    *   If it fits: Add to `current_loads`. No eviction needed.
    *   If it does not fit exactly (space < model size): Proceed to Eviction Phase.
    *   Note: "Loads cost 30s, unloads 10s" are metadata/penalties, but the core logic is capacity management. The text implies these might be counters or costs, but usually, in such problems, unless explicitly summed into a result key like `cost`, they are ignored for the final JSON. However, looking at the previous failed attempt note and the specific keys requested (`loads`, `evictions`, `deferrals`), we focus on counts.
2.  **Eviction Logic (If Load Too Big)**: If the load cannot fit:
    *   Identify "unpinned" models currently resident.
    *   Evict the Least Recently Used (LRU) unpinned model(s).
    *   Repeat eviction until enough space exists to hold the new load OR no unpinned models remain.
    *   Count each successful eviction towards `evictions`.
3.  **Deferred Load Logic**: If after exhausting all unpinned evictions, there is still not enough room (i.e., only pinned models remain and they don't fit):
    *   Mark the current load as "deferred".
    *   Increment `deferrals` count.
    *   Store the load ID in the `deferred` list.
    *   The load does **not** enter `current_loads`.
4.  **Unload Logic**: When an unload event occurs:
    *   If the model is resident: Remove from `current_loads`, free up space, increment unloads counter (metadata).
    *   If the model is not resident: No-op.
