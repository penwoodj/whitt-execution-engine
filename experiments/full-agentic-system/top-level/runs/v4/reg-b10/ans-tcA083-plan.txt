**PLAN FIRST: Step-by-step simulation plan (deterministic, integer arithmetic only)**

1. Initialize bucket state: capacity = 100, tokens = 100, refill_rate = 10 per second, current_time = 0  
2. Parse input trace: read raw request list with timestamp, weight, and index; validate timestamps and weights  
3. Validate data integrity: check for out-of-order timestamps, zero-weight requests, fractional millis  
4. Round all fractional millisecond weights to nearest integer (round half up)  
5. For each request in chronological order:  
   - Extract timestamp, weight, and index  
   - Compute time elapsed since last event (in seconds)  
   - Update bucket tokens: tokens = tokens + refill_rate * (current_time - prev_time), capped at capacity  
   - If tokens >= weight: accept request, subtract weight from tokens  
   - Else if tokens > 0: partially serve (serve tokens), update tokens to zero  
   - Else: reject request  
6. Record bucket state after each event: tokens, time, action (accept/reject/partial)  
7. After all events, compute acceptance stats per minute by binning timestamps into 60-second intervals  
8. Identify rejection spikes: find consecutive rejections with >50% of requests in a 10-second window  
9. Analyze burst dynamics: for each burst (defined as two high-weight clusters), track token drain and refill timing  
10. Edge cases logged per row: zero weight, out-of-order timestamp, fractional millisecond handling  
11. Re-run simulation with capacity = 150, same trace, compute delta in acceptance rate  
12. Output bucket.md (step-by-step state log), trace-out.jsonl (raw trace with decisions), stats.json (acceptance per minute, spikes)  
13. Write rules.md: define all policies, thresholds, rounding, ordering, and edge-case handling  
14. Write checker.py: independent script that re-computes every value from raw input; validates invariants  
15. Run simulation twice: first run to establish baseline, second run to detect state bugs (idempotent)  
16. Log per-stage timing: start time, end time, duration for each stage  
17. Generate final report with paths, timings, and one line on what surprised you  
18. Ensure every number in output is traceable to input row or computed from prior step  
19. Flag any contradiction between stated rules and actual data — if found, report it explicitly  
20. All outputs stored in /tmp/opencode/bucket-run/outputs/, scripts in /tmp/opencode/bucket-run/scripts/  
21. Final report is pasted here as plain text with full paths and timings  
22. Checker exits with non-zero code on failure; passes only if all invariants hold  
23. No interactive elements, no prompts, no hanging shells — all scripts are idempotent or self-cleaning  
24. If a rule feels arbitrary, state threshold and justification next to it  
25. When rule vs row conflict occurs, output both the row and the rule that triggered it  
26. Final report includes:  
   - Summary of simulation flow  
   - Acceptance stats (overall and per minute)  
   - Rejection spikes with timestamps and duration  
   - Burst analysis for each burst (with token drain, refill timing, edge cases hit)  
   - Capacity 150 rerun results and delta in acceptance rate  
   - All edge case types listed with handling decisions  
27. All outputs are deterministic: no randomness, no approximations, all integer arithmetic  
28. No "vibe" numbers — every percentage has a denominator (e.g., "94% of 5000 requests")  
29. If any input contradicts stated rules, report contradiction and override rule  
30. Final output is fully reproducible: given raw inputs, same outputs occur twice

**NOTES ON SPEED & INVISIBLE SHORTCUTS (to be documented in rules.md)**

- No caching of bucket state between runs — every step recomputed from prior time and refill  
- No skipping events or aggregating by minute until after full trace processing  
- All timestamps are processed in raw order; no sorting, no deduplication unless specified  
- Fractional millisecond weights rounded to nearest integer (0.5 → 1) using standard rounding  
- Out-of-order timestamp: detected and handled via policy — if a request has timestamp earlier than previous, it is rejected with note  
- Zero-weight requests: treated as valid but serve zero tokens; recorded in edge case log  
- All decisions are logged per row in trace-out.jsonl with action, tokens before/after, time
