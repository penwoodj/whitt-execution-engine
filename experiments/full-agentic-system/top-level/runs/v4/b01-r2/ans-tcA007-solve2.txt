### Phase 1: Rule Definition & Scan (Rules.md Content)

Based on the requirements for "alert storm dedup," here are the defined rules that govern state changes during processing. These rules handle grouping, noise detection, severity normalization, and data quality issues (timestamps).

**Rule ID:** `R01_GROUPING`
**Description:** Alerts with identical `message_template` are grouped into a single incident if their timestamps fall within a configurable proximity window (default: 5 minutes / 300 seconds).
**State Change:** Merges individual alerts into an `Incident` object.

**Rule ID:** `R02_TIME_QUALIFICATION`
**Description:** If an alert's timestamp is out of order relative to the stream, it is flagged as "Quarantined" but still processed for grouping logic using its actual time value.
**State Change:** Sets `is_quarantined: true` on the specific alert row; does not prevent merging if within window.

**Rule ID:** `R03_FORMAT_NORMALIZATION`
**Description:** Timestamps in mixed formats (ISO8601 vs Unix) are normalized to ISO8601. If normalization fails, the alert is marked "Rejected".
**State Change:** Converts timestamp format OR sets `is_rejected: true`.

**Rule ID:** `R04_NOISE_DETECTION`
**Description:** Any incident containing more than 10 alerts for the same template is classified as a "Noise Maker" (`is_noise_maker: true`).
**State Change:** Sets `is_noise_maker: true` on the resulting Incident object.

**Rule ID:** `R05_SEVERITY_NORMALIZATION`
**Description:** Severity levels are mapped to a standard set (Critical, Warning, Info). All-caps typos (e.g., "CRITICAL") are corrected to lowercase ("critical").
**State Change:** Updates `severity_normalized`. Corrects casing.
