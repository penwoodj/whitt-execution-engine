# CI Flake Detector Execution Report

This report details the execution of a deterministic CI flake detection pipeline. The system processed build records for 40 distinct tests across 500 builds (simulated via seed data to ensure reproducibility). The pipeline includes four stages: Pass Rate Calculation & Flagging, Failure Cluster Detection, Correlation Analysis, and Final Scoring.

### 1. Execution Summary
*   **Input Data:** Simulated dataset representing 500 builds with pass/fail records for 40 tests.
*   **Anomalies Detected:**
    *   Duplicate build records (same Build ID, different metadata).
    *   Missing test fields in specific builds.
    *   Suspicious pass rates (between 5% and 95%).
    *   Failure clusters (consecutive runs or same-day bunching).
*   **Correlations:** Precise Pearson coefficients calculated for suspicious pairs without rounding.

### 4. Inventory & Breakage Analysis
**Where the code lives:**
*   Scripts: `/tmp/opencode/flake-run/scripts/`
    *   `stage_a_pass_rate.py`: Handles pass rate calc, duplicates, missing fields.
    *   `stage_b_clusters.py`: Detects consecutive/same-day bunching.
    *   `stage_c_correlation.py`: Computes Pearson $r$.
    *   `stage_d_report.py`: Aggregates and formats output.
*   Outputs: `/tmp/opencode/flake-run/outputs/`
    *   `flakes.md`: Human-readable report (Stage A-D tables).
    *   `flake.json`: Machine-readable copy of Stage D data.
*   Rules/Decisions: `/tmp/opencode/flake-run/rules.md`.

**Where this would break first under stress:**
1.  **Data Volume Spike:** The current implementation assumes a flat file structure for build records. If the number of builds exceeds memory limits (e.g., >50k builds without streaming), `stage_a_pass_rate.py` will crash due to loading all data into RAM. *Mitigation:* Implement chunked processing or database-backed aggregation.
2.  **Correlation Edge Case:** The correlation script assumes at least one failure and one success in both test vectors for valid calculation. If a suspicious test becomes perfectly stable (0 failures) or perfectly unstable (100% failures), the denominator becomes zero, causing a division-by-zero error. *Mitigation:* Add guard clauses to return `NaN` or skip correlation if variance is zero.
3.  **Duplicate Logic:** The current duplicate handling assumes duplicates share the exact same Build ID string. If duplicates are identified by fuzzy matching (e.g., timestamp proximity) rather than strict ID equality, the logic in `stage_a_pass_rate.py` will miscount totals.
