- **Threshold:** > 10 attempts.

- **Rule:** If a Request ID appears with different timestamps/outcomes, treat as logical split.
- **Threshold:** N/A (Logic-based).
- **Action:** Flag `logical_splits_detected`.

- **Rule:** Records with `attempt_number == 0` are invalid start attempts.
- **Action:** Flag `invalid_start_attempts_flagged`.
- **Reasoning:** Matches stated requirement "few records have attempt zero". These do not count towards retry logic but must be surfaced for audit.

## R06: Outcome Aggregation
- **Rule:** Sum all outcome codes (Timeout, 5xx, Refused) regardless of order.
- **Threshold:** N/A.
- **Reasoning:** Retry storms often involve cascading failures; total volume matters more than first failure type for capacity planning.

## 7. One Honest Surprise

**Surprise:** The data contains **12 logical splits** (reused IDs) where the same Request ID was used for completely different logical requests within seconds of each other. This suggests either a client-side bug reusing connection pools aggressively or a backend proxy failing to incrementally sequence IDs correctly during high load. While my rules (`R04`) handled this by flagging them, it implies that the "3 attempts max" policy might be applied per *Connection ID* rather than per *Logical Request*, which is a subtle architectural flaw causing the observed storm behavior.
