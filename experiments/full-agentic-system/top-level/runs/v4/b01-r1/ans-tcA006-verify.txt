# Workspace Inventory & Execution Log

## 1. Decisions File (`/tmp/opencode/flake-run/.decisions.md`)

**Decision: Deterministic Seeding**
*   **Rule:** All random operations (file creation, sorting) must be seeded or deterministic to ensure bit-for-bit reproducibility across runs.
*   **Reasoning:** The task explicitly requires "deterministic or seeded so rerun gives me same universe". Without this, the `flake.json` and `flakes.md` outputs would drift between executions, failing verification.

**Decision: Data Handling for Edge Cases**
*   **Rule 1 (Duplicates):** If a build record appears multiple times with different IDs but identical content, treat as one unique data point to prevent inflating denominators artificially.
    *   **Reasoning:** Task states "some build records are duplicated... those aren't obstacles". Inflating the denominator would skew pass rates below reality.
*   **Rule 2 (Missing Fields):** If a build record has missing test fields entirely, exclude it from calculations but log it as an edge case handled by `rule_missing_fields`.
    *   **Reasoning:** Task states "three builds have missing test fields... clean run on clean data is worthless". Exclusion prevents division errors while acknowledging the anomaly.

**Decision: Output Format**
*   **Rule:** All percentages must include their denominators (e.g., `12% of 50`). No rounding to meaningless precision; keep full float for correlations.
    *   **Reasoning:** Task states "percentages need denominators next to them always" and "don't round anything into meaninglessness".

**Decision: Verification Strategy**
*   **Rule:** Run the entire pipeline twice before declaring success. Compare outputs of run 1 and run 2 for bit-for-bit equality.
    *   **Reasoning:** Task states "every stage is slow relative to its work say so honestly" (implying thoroughness) and "everything gets run twice test before you call it done".

## 3. Rules File (`/tmp/opencode/flake-run/rules.md`)

**Rule: Suspicion Threshold**
*   **Threshold:** Pass rate between 5% and 95%.
*   **Reasoning:** Task specifies "flag anything between 5 and 95 percent as suspicious". This captures the flaky zone while excluding trivially stable (>95%) or broken (<5%) tests.

**Rule: Correlation Precision**
*   **Threshold:** No rounding for correlation coefficients.
*   **Reasoning:** Task states "don't round anything into meaninglessness, i'd rather see ugly precise number".

## 5. Honest Paragraph on Breakage Points

This pipeline would break first if the input data volume exceeded memory limits of the shell scripts (e.g., >10k builds without streaming), causing `01_prepare_data.sh` to fail silently or crash. It would also break if the "deterministic" assumption was violated by external factors like non-seeded file system operations during the verification stage, leading to hash mismatches in `99_verify.sh`. Finally, it assumes the correlation metric is linear; if the failure mode of `test_retry_loop` is driven by a non-linear environmental factor (e.g., disk temperature spikes), the high correlation with `test_c` might be misleading without further domain context.
