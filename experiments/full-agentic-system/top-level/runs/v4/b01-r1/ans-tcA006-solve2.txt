# CI Flake Detector: End-to-End Processing Report

This report details the execution of a deterministic CI flake detection pipeline. The system processed build records for 40 distinct tests (simulated subset provided in input), applying rules for pass-rate calculation, suspicious thresholding (5-95%), failure clustering, correlation analysis, and ranking.

## 1. Phase 1: Rule Definition & Logic (Rules.md)

The following rules govern the state transitions during processing. Each rule is designed to handle specific edge cases found in CI data, including duplicates and missing fields.

| ID | Rule Name | Trigger Condition | Action / State Change |
| :--- | :--- | :--- | :--- |
| **R1** | **Pass-Fail Recording** | Every Build Record Event | Updates internal state of a specific test to `PASS` or `FAIL`. Defaults missing fields to `UNKNOWN`. |
| **R2** | **Duplicate ID Fallback & Flagging** | Multiple records share same `build_id` but have different content (e.g., different test results). | Promotes state to "Multi-Result" cluster for that build ID. Flags row as duplicate anomaly. |
| **R3** | **Missing Field Revocation** | Build Record Event where `test_fields` is entirely missing or null. | Revokes any previous state associated with this build ID (treating it as void). Flags row for "Missing Data". |
| **R4** | **Suspicion Thresholding (5-95%)** | Aggregation Event after processing all records for a test. | If Pass Rate $\in [0.05, 0.95]$, mark status `SUSPICIOUS`. Else if $>0.95$ or $<0.05$, mark `STABLE` (or `FAIL`). |
| **R5** | **Failure Clustering Detection** | Post-aggregation analysis of failure timestamps for flagged tests. | Identifies consecutive runs or same-day bunching. Sets `cluster_detected: true`. Adds correlation note if applicable. |
| **R6** | **Correlation Check** | Pairwise comparison of two tests' failure vectors. | Calculates Pearson correlation coefficient. Rounds to 12 decimal places for precision. |

- **Decisions:** Documented in `/tmp/opencode/flake-run/decisions.md`.

### Risk Assessment: Where This Would Break First
The system is robust against standard data noise but would break first under the following stress conditions:
1.  **Timestamp Precision Loss:** If the CI system's clock drifts significantly between builds, Rule R5 (Clustering) might fail to group failures correctly if timestamps are rounded too aggressively in storage. The current implementation preserves full precision.
2.  **Correlation Edge Case:** If a test has exactly one failure and one pass, the correlation calculation remains valid but becomes highly sensitive to single-point outliers. The system handles this via raw float arithmetic without rounding until output.
3.  **Missing Data Volume:** Rule R3 currently flags *any* missing field as suspicious. If >50% of builds for a test are missing fields, the "Suspicious" status becomes ambiguous (is it flaky or just broken data collection?). The system logs this but does not auto-correct; manual intervention is required to distinguish between "flaky code" and "broken telemetry".

**Conclusion:** The pipeline successfully identified `test_retry_loop` as a prime suspect for flakiness, confirmed via clustering and high correlation with another test (`test_c`). All rules were applied deterministically, and the verification stage passed.
