# Inventory Pipeline Rules

## Stage 1: Scan & Quarantine
- **Malformed File Quarantine**: Any JSON file with syntax errors (missing comma, trailing brace) or missing required fields (`part_id`, `category`) is moved to `quarantined/rejects/`. A reason log entry is created. Valid files are merged into the active manifest.

## Stage 2: Deduplication
- **Exact Part ID Deduplication**: If two files have identical `part_id`:
    - The file with the OLDER modification time is marked as "loser" and moved to `duplicate-losers/`.
    - The newer file remains in the active ledger.
    - A log entry records the loser's filename and reason.
- **Semantic Part Name Deduplication**: If two files have identical `part_name` AND `category` but different quantities/IDs (implied duplicate data):
    - Both entries are flagged into a "review" file (`needs_review`) rather than being silently merged or discarded.

## Stage 3: Reporting
- Calculates total distinct parts, total inventory value, defective rate %, needs review count, top 5 expensive items, and zone breakdown.

## Stage 4: Verification
- Recomputes all metrics independently from raw fixture files using separate logic (no imports of pipeline functions).
- Checks report files field-by-field against computed values.
- Exits with non-zero code on any mismatch.
- Ensures `distinct_parts + rejects + duplicate_losers` equals total input files.

## Execution Policy
- **Non-Interactive**: No prompts (`read -p`).
- **Loud Failures**: Non-zero exit codes on errors.
- **Idempotent**: Safe to run multiple times; overwrites outputs cleanly.
RULESEOF
