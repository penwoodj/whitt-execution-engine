# Final Analysis Pipeline Report

## 1. Design Normalized Schema (`schema.md`)

**Rationale:** The input data is a "messy" JSON array with nested structures, stringified currencies, and comma-separated tags. To support three constant queries (assumed: `get_products`, `get_suppliers_by_product`, `get_tag_counts`), the schema must be normalized to atomic types.

*   **Products Table:** Stores core product info.
    *   `id` (INTEGER PRIMARY KEY): Unique identifier.
    *   `name` (TEXT NOT NULL): Product name.
    *   `price_numeric` (REAL): Converted from string currency (e.g., "$10" -> 10.0).
    *   `currency_code` (TEXT): Extracted code (e.g., "USD", "EUR").
    *   `tags_json` (TEXT): Normalized list of tags as JSON array string `[["tag1","tag2"]]`.
    *   `supplier_id` (INTEGER, FOREIGN KEY): Link to Suppliers table.
*   **Suppliers Table:** Stores supplier info extracted from nested objects.
    *   `id` (INTEGER PRIMARY KEY).
    *   `name` (TEXT NOT NULL).
    *   `contact_info` (TEXT).
*   **Tags Table:** (Optional for normalization, but kept in JSON column above for query simplicity unless specific tag-level queries exist; based on "three queries" constraint usually implying product-centric views, we keep tags as a list in Products to avoid many-to-many complexity if not strictly required. However, strict normalization suggests a separate Tags table. Given the instruction "nested suppliers, tags as comma strings", I will implement a **Many-to-Many** approach via a `product_tags` junction table for true normalization).
    *   *Correction:* To ensure "sane typed schema" and support queries like "products with tag X", a junction table is best.
    *   `product_id` (INTEGER, FK).
    *   `tag_name` (TEXT NOT NULL).

**Final Schema Definition:**

```sql
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    price_numeric REAL,
    currency_code TEXT,
    supplier_id INTEGER,
    FOREIGN KEY (supplier_id) REFERENCES suppliers(id)
);

CREATE TABLE suppliers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    contact_info TEXT
);

CREATE TABLE product_tags (
    product_id INTEGER NOT NULL,
    tag_name TEXT NOT NULL,
    PRIMARY KEY (product_id, tag_name),
    FOREIGN KEY (product_id) REFERENCES products(id)
);
```

**Rules Invented:**
1.  **Currency Conversion Rule:** Any price string containing a currency symbol (`$`, `€`) must be parsed to extract the numeric value and the code. If no symbol is found but text exists, assume USD unless specified otherwise (default).
2.  **Tag Splitting Rule:** Comma-separated strings in input must be trimmed of whitespace and split into individual tags. Empty strings resulting from consecutive commas are discarded.
3.  **Nested Object Flattening Rule:** If a record is an array itself (e.g., `{"data": [...]}`), the first element is treated as the product object; subsequent elements are ignored or logged as "array anomaly".

## 3. Indexes for Three Known Queries (`verify_script`)

**Assumed Queries:**
1.  `SELECT * FROM products WHERE name LIKE '%keyword%';` (Text search)
2.  `SELECT p.*, s.name AS supplier_name FROM products p JOIN suppliers s ON p.supplier_id = s.id;` (Join query)
3.  `SELECT product_id, COUNT(*) as tag_count FROM product_tags GROUP BY product_id;` (Aggregation)

**Indexing Strategy:**
*   **Query 1:** Index on `products.name`.
    *   *Note:* Full-text search is better for "LIKE", but B-Tree index helps with prefix matches. We create a standard index.
*   **Query 2:** Foreign Key relationship already indexed by SQLite (`supplier_id` FK). No extra index needed, but we verify the join path.
*   **Query 3:** Index on `product_tags.product_id`.
