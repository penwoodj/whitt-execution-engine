1. **Initialize workspace**: Create `/tmp/opencode/routing-run` with subdirectories: `data/`, `stages/`, `outputs/`, `logs/`, `decisions.md`.  
2. **Load raw data**: Read all 1000 tickets from `data/raw_tickets.csv` into memory; parse fields: subject, body, product, severity, final_queue, and optional comment (for renaming).  
3. **Extract queue name mapping**: Parse the comment field to extract old-to-new queue name mappings; record in `stages/queue_mapping.json`.  
4. **Identify double-routed tickets**: Flag all tickets with more than one queue label; store list in `stages/double_route_report.md` and `stages/double_route_tickets.csv`.  
5. **Split data**: Split 1000 tickets into training (800) and holdout (200), preserving original order and metadata; save to `data/train.csv`, `data/holdout.csv`.  
6. **Derive keyword rules from training set**:  
   - For each unique phrase in the subject/body, count its co-occurrence with final_queue.  
   - Build candidate rule: (phrase → queue) with support count = number of tickets containing phrase and routed to that queue.  
   - Compute precision for each rule: (support count) / (total tickets where phrase appears), across all queues.  
   - Filter rules by minimum support ≥ 1, and precision ≥ 0.5; save as `stages/keyword_rules.csv`.  
7. **Compute rule performance on holdout**:  
   - Apply every derived keyword rule to each of the 200 holdout tickets.  
   - For each ticket, record: predicted queue(s), actual final_queue, and all rules that triggered it.  
   - Compute overall accuracy (correct predictions / total) and per-queue accuracy.  
   - Identify confusion pairs: (queue A, queue B) where at least 5% of tickets were routed to both or misrouted between them.  
   - Save results in `outputs/holdout-scores.json` and `stages/holdout_analysis.csv`.  
8. **Generate ambiguity report**:  
   - For each confusion pair (A, B), list all phrases that appear in tickets routed to A or B.  
   - Rank phrases by frequency of appearance in either queue.  
   - Identify top 5 phrases per pair; save as `outputs/ambiguity_report.md`.  
9. **Construct final decision rule set**:  
   - Order rules by: (1) phrase length, (2) support count descending, (3) precision descending.  
   - Apply tie-breaking: if two rules have same phrase and support, prefer the one with higher precision.  
   - Ensure first-match-wins behavior; write as ordered list in `outputs/rules.md`.  
10. **Write routing.md**: Summarize rule set structure, including queue names, thresholds (if any), and rationale for each rule’s threshold or inclusion.  
11. **Run checker script**:  
    - Recompute all stages from raw data using the same inputs and logic.  
    - Verify:  
      - All rules are derived only from training tickets.  
      - Holdout accuracy matches computed value.  
      - Double-routed tickets are correctly flagged.  
      - Queue name mapping is applied consistently.  
      - No rule uses a phrase not present in raw data.  
    - Output checker results to `stages/checker_output.json`.  
12. **Log stage timings**: Record start/end timestamps for each step; save as `logs/stage_timings.csv`.  
13. **Document decisions**: In `decisions.md`, list:  
    - All assumptions (e.g., min support = 1, precision threshold = 0.5).  
    - Why certain rules were included or excluded.  
    - How double-routed tickets were handled.  
    - Any data contradictions found (e.g., queue name change not in comment field).  
14. **Validate outputs**:  
    - Compare human-readable markdown (`outputs/*.md`) with machine-readable JSON (`outputs/*.json`).  
    - Ensure all numbers match exactly; flag mismatches.
