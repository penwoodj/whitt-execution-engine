Phase 1 RULE SCAN:

- Rule: Apply median-of-repeats policy uniformly across all workloads and systems; triggered by raw benchmark output arrival.  
  Threshold: All repeats must be present and non-empty; if any repeat is missing or empty, mark as error with timestamp.  
  Reason: Ensures robustness against noise and caching; median resists outliers better than mean.

- Rule: Detect best-per-column winner per workload; triggered when raw benchmark output is parsed into a table.  
  Threshold: If multiple systems tie for best in a column (e.g., same time), mark all tied entries as "tie" with explicit note.  
  Reason: Prevents arbitrary selection; ties must be visible and verifiable.

- Rule: Render ncr cells distinctly with crash reason from raw logs preserved; triggered when system crash is detected in raw logs.  
  Threshold: If log contains "crash", "exit code != 0", or "segmentation fault" within workload run, mark as ncr.  
  Reason: Ensures failure visibility and traceability to source.

- Rule: Apply relative-to-best row per workload (percent slower); triggered after best-per-column is determined.  
  Threshold: Only compute if a valid best exists; if no best, skip or flag error.  
  Reason: Provides meaningful performance comparison against baseline without rounding.

- Rule: Normalize units across workloads using column-specific scaling factors; triggered when unit mismatch is detected in raw data.  
  Threshold: If any workload uses different units (e.g., ms vs μs), apply per-column normalization via conversion factor derived from known reference values.  
  Reason: Enables fair comparison without arbitrary scaling.

- Rule: Flag and preserve all byte-identical repeats as caching evidence; triggered when two repeats are bit-for-bit identical in raw output.  
  Threshold: If hash of repeat A == hash of repeat B, record as "caching detected" with timestamp and file path.  
  Reason: Exposes pipeline artifacts that may skew results; must be reported transparently.

- Rule: When a workload has only two repeats, treat it as incomplete and flag for manual review; triggered when repeat count < 3 per workload.  
  Threshold: Any workload with fewer than three repeats triggers this rule.  
  Reason: Ensures data completeness; under-replicated runs lack statistical validity.

- Rule: State median-of-repeats policy in a footnote table draft; triggered after first full parse of raw output.  
  Threshold: Policy must be written verbatim and included in policy.md.  
  Reason: Verifier needs to independently validate the choice, not rely on narrative.

- Rule: When a rule and row disagree (e.g., median vs best), both go into output with side-by-side display; triggered during final table generation.  
  Threshold: Any conflict between rule logic and data must be surfaced in output.  
  Reason: Ensures transparency of decision boundaries.

- Rule: If raw data contradicts stated task assumptions, report contradiction immediately; triggered at any stage where input violates prior constraints.  
  Threshold: E.g., if a workload has three repeats but two are identical and one is missing — flag as contradiction.  
  Reason: Data must win over assumed structure; avoids silent bending.

- Rule: All outputs (table.md, table.json, policy.md) generated with full path in report; triggered at final stage of pipeline.  
  Threshold: Paths must be absolute and match workspace layout.  
  Reason: Enables direct verification by human or verifier.

- Rule: Pipeline runs twice before final output; triggered after every stage except the last.  
  Threshold: First run completes successfully; second run must produce identical results.  
  Reason: First run may succeed due to caching or timing; second run exposes state bugs.

- Rule: All stages are idempotent or self-cleaning; triggered at design phase of scripts.  
  Threshold: Scripts must either accept input and return same output, or clean up prior artifacts on re-run.  
  Reason: Ensures reproducibility without hidden side effects.

- Rule: Any stage with slow runtime relative to work is explicitly noted; triggered during timing analysis.  
  Threshold: If a stage takes >10 seconds per run, note it in the timings table.  
  Reason: Prevents performance bias from being masked as "normal".

- Rule: Percentages must include denominators (e.g., "23% of best time"); triggered when computing relative performance.  
  Threshold: All percentages must be labeled with what they represent.  
  Reason: Avoids ambiguity; a percentage without context is meaningless.

- Rule: Final output numbers are derived from actual runs, not approximated; triggered at every numeric computation step.  
  Threshold: Every number in final table must trace back to raw input row.  
  Reason: Ensures no "should-be" or "roughly" values exist — all results are computed and verifiable.
