# CI Flake Detector Report

## Executive Summary
This report details the findings of a deterministic, self-contained analysis of build records from a CI system that ran 500 builds over a month. The analysis focuses on identifying flaky tests—those that pass and fail without code changes—with specific attention to `test_retry_loop`. All processing was performed using standard Python libraries in `/tmp/opencode/flake-run`, ensuring reproducibility (bit-for-bit identical results upon rerun).

**Key Findings:**
- **Suspicious Tests Identified:** 2 tests (`test_retry_loop`, `test_memory_leak`) exhibit pass rates between 5% and 95%.
- **Failure Clusters:** Both suspicious tests show consecutive failures in the dataset.
- **Correlations:** No statistically significant correlation found between `test_retry_loop` and `test_memory_leak`.
- **Data Anomalies Handled:** Duplicate build records and missing test fields were logged and resolved according to defined rules.

## 2. Rules & Policies (`RULES.md`)

### Rule R1: Suspicion Threshold
- **Logic:** A test is suspicious if its pass rate $P$ satisfies $0.05 \le P \le 0.95$.
- **Reasoning:** Tests with $P > 0.95$ are effectively stable; tests with $P < 0.05$ are effectively broken. The "flaky" behavior occurs in the middle ground where outcomes vary significantly without code changes.

### Rule R2: Cluster Definition
- **Logic:** A failure cluster is defined as $\ge 3$ consecutive failures for a specific test within the build sequence.
- **Reasoning:** Isolated failures can be noise; clusters indicate systemic instability or environmental triggers.

### Rule R3: Correlation Metric
- **Logic:** Calculate Pearson correlation coefficient ($r$) between binary failure vectors of two tests.
- **Precision:** No rounding applied to $r$.
- **Threshold for "Correlated":** $|r| > 0.5$.

### Rule R4: Data Anomaly Handling
- **Duplicate Builds:** If `build_id` differs but test content is identical, log as `[DUPLICATE]`. Do not merge unless a specific rule dictates otherwise.
- **Missing Fields:** If a build record lacks a pass/fail value for a test, log as `[MISSING_DATA]` and exclude that specific data point from the pass rate calculation (denominator adjustment).

## 6. Inventory & Risk Assessment

### Inventory
- **Scripts:** `stage1.py`, `stage2.py`, `stage3.py`, `verifier.py` located in `/tmp/opencode/flake-run/scripts/`.
- **Outputs:** `flakes.md` and `flake.json` located in `/tmp/opencode/flake-run/outputs/`.
- **Rules:** Defined in `/tmp/opencode/flake-run/RULES.md`.

### Where This Would Break First (Risk Assessment)
If the CI system were stressed harder, this analysis would break first at:
1.  **Data Volume Spike:** The current script assumes a manageable dataset for memory mapping. A sudden influx of >50k builds without streaming logic would cause OOM errors in `stage1.py`.
2.  **Correlation Sensitivity:** With only 40 tests, the correlation matrix is small but sensitive to outliers. If a new test with extreme variance (e.g., 50% pass rate) was introduced, it could skew the global correlation baseline if not filtered.
3.  **Determinism Assumption:** The analysis assumes build order is fixed. If the CI scheduler randomizes build execution order dynamically between runs, the "consecutive failure" clusters identified in Stage 2 would shift, invalidating the cluster counts unless timestamps are used to anchor the sequence rather than build ID order.
