**Decisions & Defaults (`README.md`):**
*   **Input Simulation:** Since no actual `products_raw.json` was provided in the prompt context, a deterministic mock dataset of 3 records is generated to demonstrate handling of specified edge cases (missing fields, nested arrays, currency symbols).
*   **Currency Handling:** Prices containing non-USD symbols (e.g., "€", "£") are stripped of the symbol but kept as strings. They are NOT converted to floats unless explicitly USD.
*   **Tag Parsing:** Comma-separated tags in input strings are split into a JSON array. Whitespace is trimmed. Empty strings resulting from consecutive commas are removed.
*   **Nested Arrays:** Records where the entire value of a field (e.g., `suppliers`) is an array instead of an object are flattened: `[{"id": 1, "name": "A"}, {"id": 2, "name": "B"}]` becomes a single JSON string representation or a list of dicts depending on schema strictness. Here, we store as a JSON string to preserve structure in `TEXT` columns if needed, but the schema defines it as `JSON`.
*   **Missing Fields:** Required fields (`id`, `name`) missing entirely cause record rejection with specific error logging.

**Invented Rules & Thresholds (`rules.md`):**
1.  **Tag Splitting Rule:** If a tag string contains commas, split by `,`. Denominator: Total comma count + 1. Result must be trimmed and non-empty.
2.  **Currency Strip Rule:** Regex `^[A-Z]$` matches currency symbols at start of price string. Action: Remove match. Threshold: 0% tolerance for remaining symbols.
3.  **Nested Supplier Flattening Rule:** If `suppliers` field is a list, convert to JSON string. Rationale: Preserve nested structure without schema violation if input was malformed.
4.  **Rejection Threshold:** Any record missing `id` or `name` (case-insensitive check on key existence) is rejected. Denominator: Total records processed.

## 2. Schema Design (`schema.md`)

**Rationale:**
The goal is a "sane typed schema" that normalizes messy inputs while preserving data integrity for downstream queries. We use `JSON` types for flexible nested structures (tags, suppliers) to avoid complex SQL parsing in application logic, and strict `TEXT`/`REAL` for atomic values.

**Products Table:**
*   `id`: `INTEGER PRIMARY KEY` (Auto-increment surrogate if input ID missing, or stored value).
*   `name`: `TEXT NOT NULL` (Atomic product name).
*   `price`: `TEXT` (Stores raw price string with currency stripped; allows future conversion logic).
*   `tags`: `JSON` (Normalized array of strings: `[{"tag": "electronics"}, {"tag": "sale"}]`).
*   `currency`: `TEXT DEFAULT 'USD'` (Explicitly set to 'USD' after stripping symbols, or kept as input if ambiguous but normalized).

**Suppliers Table:**
*   `id`: `INTEGER PRIMARY KEY`.
*   `product_id`: `INTEGER FK REFERENCES products(id)`.
*   `name`: `TEXT NOT NULL`.

*(Note: The prompt's initial JSON snippet suggested a different structure for suppliers, but the "sane typed schema" requirement implies normalizing nested supplier data into a relational table.)*
