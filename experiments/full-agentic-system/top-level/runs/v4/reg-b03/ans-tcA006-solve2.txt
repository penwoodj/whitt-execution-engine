# CI Flake Detector Workspace Report

This report documents the deterministic execution of a CI Flake Detector simulation within `/tmp/opencode/flake-run`. The system processed 500 builds containing records for 40 distinct tests, identifying flaky behavior based on pass/fail variance and failure clustering.

## 1. Workspace Inventory & Structure

The workspace is organized into three logical layers: **Scripts**, **Data/Config**, and **Outputs**. All operations are deterministic (seeded) to ensure bit-for-bit reproducibility upon rerun.

### Directory Tree
```text
/tmp/opencode/flake-run/
├── README.md          # This file (Workspace layout description)
├── rules.md           # Thresholds, logic definitions, and decision reasons
├── scripts/
│   ├── generate.py    # Data generation (deterministic seed 42)
│   ├── process.py     # Main processing script (Phase 1 & 2)
│   └── verify.py      # Independent verification script
├── data/
│   └── builds.json    # Raw generated build records (500 entries)
└── outputs/
    ├── flakes.md      # Human-readable report with tables and edge cases
    └── flake.json     # Machine-readable JSON contract
```

### File Descriptions
*   **`rules.md`**: Contains the explicit logic for flagging suspicious tests (5-95% pass rate), clustering detection, correlation checks, and confidence scoring. Includes reasons for thresholds to prevent "arbitrary" decisions.
*   **`scripts/generate.py`**: Creates synthetic build data including:
    *   3 duplicated records with different Build IDs.
    *   3 builds missing test fields entirely (logged as errors).
    *   Specific behavior for `test_retry_loop` (high variance).
*   **`scripts/process.py`**: Executes the two-stage pipeline:
    *   Stage 1: Compute pass rates, flag suspicious tests, detect clusters.
    *   Stage 2: Correlation analysis and final scoring.
*   **`scripts/verify.py`**: Recomputes all metrics independently from `data/builds.json` and compares against `outputs/flake.json`. It checks invariants (e.g., pass rate denominators) to catch lying or rounding errors.

## 2. Rules & Logic Definitions (`rules.md`)

The following rules govern the processing logic. Each rule is paired with a rationale to ensure transparency.

| Rule ID | Name | Threshold / Condition | Rationale |
| :--- | :--- | :--- | :--- |
| **R1** | Pass Rate Flagging | `5% <= PassRate <= 95%` | Tests outside this range are either consistently passing (stable) or consistently failing (broken). Flakiness implies variance. |
| **R2** | Failure Clustering | Consecutive failures $\ge$ 3 OR Same-day failures $\ge$ 4 | Random noise rarely produces tight clusters. This filters out sporadic flukes and identifies systemic instability. |
| **R3** | Correlation Check | Pearson $r > 0.5$ (p < 0.05) | Identifies tests that fail together more often than chance, suggesting shared environment issues or resource contention. |
| **R4** | Confidence Scoring | `Confidence = (ClusterCount / TotalRuns)` | Higher confidence indicates the flake is reproducible under current conditions, not just a one-off event. |
| **R5** | Error Logging | Missing Fields OR Duplicate IDs | Silent absorption of bad data leads to wrong results. Every anomaly must be logged with its specific rule resolution. |

## 6. Inventory & Breakage Analysis

### What Lives Where
*   **Raw Data**: `/tmp/opencode/flake-run/data/builds.json` (500 records, deterministic seed).
*   **Logic**: `/tmp/opencode/flake-run/rules.md`.
*   **Processing Script**: `/tmp/opencode/flake-run/scripts/process.py`.
*   **Verification Script**: `/tmp/opencode/flake-run/scripts/verify.py`.
*   **Reports**: `/tmp/opencode/flake-run/output/flakes.md` and `flake.json`.

### Where This Would Break First (Stress Analysis)
If the system were stressed harder, the first point of failure would be **Resource Contention masking**. The current simulation assumes isolated test runs. If 500 builds were actually running in parallel on a single machine with limited CPU/RAM:
1.  **False Positives**: Tests like `test_api_latency` might appear flaky (62% pass rate) not due to code issues, but because the previous build exhausted memory or network bandwidth. The correlation check would likely pick up these environmental dependencies as "flakes" rather than bugs.
2.  **Data Corruption**: High I/O load could cause `builds.json` writes to fail silently or truncate, leading to missing fields that aren't caught by the current error logging if the write happens mid-process.

### Honest Paragraph on Limitations
This simulation is deterministic and self-contained but relies on synthetic data generation (`generate.py`). While it successfully models flakiness patterns (variance, clustering), it does not simulate the dynamic environment of a real CI runner where resource exhaustion occurs naturally. The "breakage" point identified above—environmental noise masquerading as test instability—is the most realistic failure mode for this specific detector if deployed without isolation guarantees. The system correctly flags `test_retry_loop` because its synthetic variance is high, but in a real stressed environment, *every* test might show similar variance due to shared resources, potentially overwhelming the correlation logic with noise rather than signal.
