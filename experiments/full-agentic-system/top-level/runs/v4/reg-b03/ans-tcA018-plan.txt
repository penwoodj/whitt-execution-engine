### Step 1: Initialize Workspace & Decisions Log
**Rule:** Create `/tmp/opencode/perf-reg-run` with subfolders `raw`, `norm`, `delta`, `audit`, `report`, `logs`. Write `decisions.md` documenting all arbitrary choices (e.g., handling single repeats, outlier rejection thresholds, timestamp tie-breaking).

### Step 2: Normalize Repeats
**Rule:** Read raw timing files. For each scenario/commit pair with $N \ge 3$ repeats, compute Median and Best (Min). If $N=1$, flag as `SINGLE_REP` in audit log but include the single value as both median and best without statistical smoothing.

### Step 3: Compute Commit-Over-Commit Deltas
**Rule:** Sort commits by timestamp; if timestamps are identical, use commit hash lexicographically (first byte) to break ties deterministically. Calculate $\Delta = \frac{V_{new} - V_{old}}{V_{old}} \times 100$. Output full precision floats (no rounding) in `delta/`.

### Step 4: Stage 1 Audit (Regressions & Refactor Check)
**Rule:** Flag scenarios where $|\Delta| > 10\%$ as `REGRESSION`. Specifically inspect the "pure refactor" commit; if any scenario shows $\Delta \neq 0$, mark it `REFACTOR_FAIL` in `audit/`. Document every flagged row with its rule citation.

### Step 5: Stage 2 Audit (Scenario Verdicts & Overall Commit Verdict)
**Rule:** Assign verdicts: `CLEAN`, `REGRESSED`, or `IMPROVED`. Determine overall commit status based on majority scenario verdicts. If a single outlier spike exists, apply the "Quarantine" rule from `decisions.md` (reject if $>3\sigma$ deviation) and note in audit log.

### Step 6: Generate Human & Machine Reports
**Rule:** Create `perf.md` with Markdown tables (Human Table). Create `perf.json` with identical numeric values (Machine Copy). Ensure no drift between files. Include "Warts" section listing ambiguous timestamps, single repeats, and outliers explicitly.

### Step 7: Verification Script Execution
**Rule:** Run independent `verify.sh` script that recomputes all metrics from raw timing files using separate logic. Compare field-by-field against `perf.json`. Exit non-zero on any drift. Output verification log to `logs/verify.log`.

### Step 8: Idempotency & Double-Run Test
**Rule:** Execute the entire pipeline twice. Verify that outputs are identical (idempotent) or self-cleaning between runs. Log timestamps for each stage execution in a final timing table.

### Step 9: Final Deliverables Assembly
**Rule:** Generate `README.md` pointing to all artifacts, decisions file, and verification logs. Include the "One Honest Surprise" section documenting any unexpected data behavior (e.g., the refactor commit actually regressing).
