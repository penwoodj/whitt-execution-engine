### 2. Implementation Details

#### A. Fixture Data Generation (`data/`)
The data generation logic creates exactly 200 valid JSON records distributed across the four subfolders. It intentionally includes:
*   **Malformed Records:** Missing commas, trailing braces (e.g., `{"part_id": "PTM-1",`), and missing fields.
*   **Duplicates:** Exact same `part_id` appearing in different files with newer modification times to test deduplication logic.
*   **Variety:** Randomized categories (`fastener`, `electrical`, etc.), quantities (including 0), unit costs, and statuses (`ok`, `needs_review`, `defective`).

#### B. Pipeline Logic (`scripts/pipeline.py`)
The pipeline executes in three stages:

1.  **Stage 1: Scan & Merge**
    *   Scans all four folders recursively.
    *   Parses valid JSON records into a manifest list.
    *   Identifies malformed files and writes them to `data/rejects.json` with the filename and error reason (e.g., "JSONDecodeError").

2.  **Stage 2: Deduplication**
    *   **Exact ID Match:** If two records share the same `part_id`, the one with the newer file modification time is kept; the other is logged to `data/duplicate_losers.json`.
    *   **Category/Name Ambiguity:** Records with identical `part_name` and `category` but differing quantities are flagged as potential duplicates and written to `data/review_candidates.json`.

3.  **Stage 3: Reporting**
    *   Computes metrics from the deduplicated manifest:
        *   Total distinct parts count.
        *   Total inventory value (sum of quantity * unit_cost).
        *   Per-category breakdowns.
        *   Defective rate percentage.
        *   Top 5 most expensive single items.
    *   Writes `warehouse-report.md` (human-readable) and `warehouse-report.json` (machine-readable).

#### C. Verification Logic (`scripts/verify.py`)
The verification script is completely independent of the pipeline's internal functions:
*   It re-scans the raw fixture files to count total inputs.
*   It reads `data/rejects.json`, `data/duplicate_losers.json`, and `data/review_candidates.json` to calculate expected distinct parts.
*   It parses the generated report files (`warehouse-report.md` and `warehouse-report.json`) to extract reported numbers.
*   **Strict Checks:** Ensures counts match exactly (e.g., if Markdown says 14 defective, JSON must say 14). If any mismatch occurs, it exits with a non-zero code and prints the discrepancy.

#### D. Efficiency Version
The efficiency version is achieved by optimizing file I/O:
*   Uses `pathlib` for efficient path handling.
*   Batches file reads where possible (though JSON parsing is inherently sequential).
*   Avoids unnecessary string conversions during numeric calculations.
*   The output files are byte-for-byte identical to the standard version, ensuring no drift in reporting logic.
