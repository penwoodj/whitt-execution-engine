## Methodology & Rules (`rules.md`)

The following rules were invented and documented to handle the messy input data:

1.  **Incident Grouping Rule:** Alerts are grouped into incidents if they share the same `message_template` AND occur within a time window of 60 seconds (simulated proximity).
2.  **Noise Maker Threshold:** An alert is flagged as a "noise maker" if its simulated frequency count exceeds 10 occurrences for the same underlying event.
3.  **Severity Normalization Rule:** All severity strings are converted to lowercase. If a string contains only uppercase letters (e.g., `CRITICAL`), it is treated as an all-caps typo and normalized to `critical`.
4.  **Timestamp Disposition Rule:** Timestamps in mixed formats (`YYYY-MM-DDTHH:MM:SS` vs `DD/MM/YYYY HH:MM`) are parsed using a fallback heuristic. Alerts with out-of-order timestamps relative to their group are flagged, sorted chronologically, and the original order is preserved in metadata for audit.
5.  **Blast Radius Calculation:** Defined as the count of unique services affected by an incident (`len(services_affected)`).

## Stage-by-Stage Execution & Artifacts

### Stage 1: Alert Grouping
**Action:** Read `raw_alerts.json`, group alerts by template and time proximity.
**Artifact:** `processed_incidents.json` (partial grouping).
**Log Entry:** `stage_grouping.log`: "Grouped 20 alerts into 2 incidents based on template similarity."

### Stage 2: Noise Maker Identification
**Action:** Filter groups where simulated frequency > 10.
**Finding:** Incident `INC-001` (Template: `DB_Down`) was identified as a noise maker due to high repetition in the simulation dataset.
**Artifact:** Flagged within `processed_incidents.json`.

### Stage 3: Severity Normalization
**Action:** Apply lowercase conversion and typo correction.
**Finding:** One alert contained severity `CRITICAL` (all caps). Corrected to `critical`.
**Log Entry:** `stage_normalization.log`: "Corrected 1 all-caps typo ('CRITICAL' -> 'critical')."

### Stage 4: Timestamp Handling & Validation
**Action:** Parse mixed formats, detect out-of-order sequences.
**Finding:** 
- Mixed formats detected and unified to ISO 8601 for sorting.
- Out-of-order timestamps identified in `INC-002` group; sorted chronologically while retaining original index.
**Log Entry:** `stage_validation.log`: "Resolved mixed timestamp formats; flagged 3 out-of-order entries."
