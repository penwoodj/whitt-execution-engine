1. Read input files (ramp.json) to extract raw time-series data: users, throughput, p95 latency, error rate, with timestamps, every 10 seconds from t=0 to t=30 minutes.  
2. Parse ramp.json into structured arrays: each row is [timestamp, virtual_users, throughput, p95_latency, error_percent] — validate schema and units (e.g., users must be integers, percentages must have denominator).  
3. Validate data integrity: check for missing samples at critical points (e.g., 10–600 user range), detect counter resets (e.g., sudden drop in throughput after 5 minutes), flag inconsistencies in units or values.  
4. Build a table of raw data per 10-second interval, ordered chronologically by timestamp, with full column headers and units: users, throughput (req/sec), p95 latency (ms), error rate (% of total samples).  
5. Identify the "knee" point in degradation: compute slope of throughput vs. user count and slope of p95 latency vs. user count over each 10-second interval; find where latency growth exceeds throughput growth by more than 0.02 req/sec per user (threshold chosen for statistical significance).  
6. Determine graceful degradation claim: define "graceful" as error rate ≤ 1% and throughput ≥ 80% of baseline until 600 users, then verify that after 600 users, either error rate exceeds 1%, or throughput drops below 80% of baseline at any point.  
7. Categorize errors by type: classify each error (e.g., "timeout", "connection refused", "5xx") from error_percent field using a rule-based taxonomy — if no label exists, flag as "unknown". Assign per-interval counts and percentages with denominators (e.g., 12% of 300 samples).  
8. Detect edge cases: any interval where users jump >100, or throughput drops by more than 50%, or error rate spikes to >5%, record explicitly in output with timestamp and value.  
9. Generate knee.md one-pager: explain method (slope comparison), threshold (0.02 req/sec/user), data range used, and the exact interval where knee occurs. Include raw values from input at that point.  
10. Output ramp.md: human-readable table of all intervals with users, throughput, p95 latency, error rate — same as in step 4, formatted for skimming.  
11. Output ramp.json: machine-readable version of the same data, with metadata (timestamp range, units), and flags for edge cases and validation errors.  
12. Run full pipeline twice: first run to establish baseline; second run to detect state-dependent bugs (e.g., counter resets, missing samples). Compare outputs — if any row differs, log discrepancy.  
13. Write rules.md: list all thresholds and decisions with rationale: e.g., "knee threshold = 0.02 req/sec/user because it matches observed degradation in prior runs", "error rate >5% triggers edge case flag due to real-world system instability at that level".  
14. Create verify.sh script: a standalone script that reprocesses ramp.json, recomputes all values independently, and compares outputs numerically (within 0.01%) with existing ramp.md/ramp.json. It must pass strict equality checks on every row and invariant (e.g., total intervals = 360).  
15. Write decisions.txt: list all assumptions made — e.g., "assumed throughput units are req/sec", "assumed p95 latency in ms", "used 10-second interval as step size", "baseline throughput at 10 users is 2.4 req/sec".  
16. Generate timing log per stage: one line per stage with timestamp (e.g., "Stage 1: parsed ramp.json at 2025-04-05T10:00:32Z").  
17. Write README.md: points to all files, explains workflow in plain English, lists stages, and states that the pipeline is reproducible from source.  
18. Detect contradiction between input claim and data: if ramp says "degraded gracefully past 600 users" but data shows error rate >2% at 700 users or throughput drops below 90%, report it explicitly with timestamps.  
19. Final output includes one honest surprise: e.g., "At t=1800s, user count jumps from 590 to 610 without ramping — this violates the assumed linear ramp and may indicate a system bug or misconfiguration."
