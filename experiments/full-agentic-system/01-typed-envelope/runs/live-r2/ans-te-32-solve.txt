### Phase 1: RULE SCAN

The following rules govern the state changes during tonight's rotation events. Rules are listed in order of precedence (higher in the list applies first if there is a conflict, though the logic here dictates a strict sequence).

1.  **Arrival Rule**: When a job arrives at minute $T$, it enters the `queued` or `running` state based on core availability; if the core is busy, it waits until that specific busy period ends before transitioning to `running`.
2.  **Preemption Rule (HIGH)**: Upon arrival of a HIGH job, if the core is running a LOW job, the current LOW job is immediately preempted (state change `running` $\to$ `stopped_preempted`), and its elapsed time resets for the purpose of future checkpoint calculation; the HIGH job transitions to `running`.
3.  **Checkpoint Rule**: A LOW job increments its "completed minutes" counter by its runtime duration every minute it runs, but logically checkpoints occur at milestones (0, 2, 4...). The work done since the last checkpoint is considered valid only if the job finishes; otherwise, work past the last completed milestone is wasted.

    *   *Logic*: Work accumulates continuously. A "checkpoint" validates progress up to that point. If interrupted between checkpoints (or exactly at a non-checkpoint boundary), the unvalidated portion is lost.
    *   *Specific interpretation for this text*: Checkpoints are valid boundaries. Work done in intervals $[0, 2)$, $[2, 4)$, etc., is saved if the job reaches that integer time. If preemption happens at minute $T$, and there was no checkpoint at $T$ (i.e., $T$ is odd), then $1$ minute of work in the current interval is wasted.
4.  **Resume Rule**: When a preempted LOW job resumes, it continues from its last saved state (last valid checkpoint time). Any runtime accumulated between that checkpoint and preemption is discarded (wasted).
5.  **Completion Rule**: A job finishes when its `remaining_duration` hits 0. The completion order is determined by the actual finish times of these events.
6.  **Makespan Definition**: Calculated as `max(finish_time_of_any_job) - min(start_time_of_any_job)`.
7.  **Expiry/Return Rule (Implicit)**: Not triggered here as there are no budget limits or refunds mentioned, only resource contention and checkpoint loss.
