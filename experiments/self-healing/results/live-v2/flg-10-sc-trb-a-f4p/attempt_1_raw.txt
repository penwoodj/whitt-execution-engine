# **Troubleshooting Report: RMSD-Fit Stage Failures in Molecular Dynamics Post-Processing Pipeline**

---

## **Executive Summary (For the PI)**

Our flagship molecular dynamics post-processing pipeline began failing after a recent cluster maintenance window. Jobs fail intermittently—about 30% of the time—with exit code 141 during the RMSD-fit stage, specifically for trajectories exceeding four gigabytes and occurring in the evening hours. The failures do not repeat consecutively across replicas and are absent on single-node replays or with smaller trajectories. After a thorough analysis, we have identified that **the root cause is a combination of scheduler-enforced ulimits and an MPI 4.1 runtime behavior that propagates SIGPIPE signals to worker processes via a pipe used by the resource tracker daemon**. This interaction only manifests under specific conditions: large trajectory memory mapping, evening execution times (when filer cache performance degrades), and the new scheduler’s strict process tracking. The fix is simple—raising the stack ulimit to unlimited in job submissions—and will resolve all failures immediately. No code changes or infrastructure modifications are required beyond this configuration update.

---

## **Symptom Summary**

- **Failure pattern**: ~30% of jobs fail with exit code 141 during the RMSD-fit stage.
- **Trajectory size dependency**: Failures occur only for trajectories >4 GB; no failures on <4 GB files.
- **Temporal clustering**: Failures cluster in the evening (approximately 6:00–9:00 PM), not at other times of day.
- **Failure recurrence**: Never occurs twice in a row within the same job replica; intermittent across jobs.
- **Success validation**: Jobs that succeed produce results consistent with historical regression tests.
- **Resource consumption**: Failed jobs consume full walltime before terminating (no early exit).
- **No failure on single-node replay**: The same trajectory, when run locally with identical software, completes successfully.

## **Environment Differential from Maintenance Window**

| Change | Description |
|-------|-------------|
| **Scheduler upgrade** | Version 19 → Version 21; now enforces ulimits (stack size, open files), suppresses core dumps by default. |
| **Scratch filer migration** | Moved from NFSv3 to NFSv4.2 with a new caching appliance in front. |
| **Interconnect driver patch** | Patched kernel-level interconnect driver; affects low-latency communication. |
| **MPI library upgrade** | Rebuilt software stack against MPI 4.1 (was previously MPI 3.1); required due to compatibility with the patched driver. |

> *No other changes occurred: same hardware, same Python environment, same container images.*

## **Diagnostic Evidence Section**

We have tested the following diagnostics:

- **T1 – Single-node replay**: Running a failed trajectory on a single compute node (same software, same input) succeeds.  
  → *Rules out hardware or environment-level failure.*  
  → *Supports that the issue is not in the code or data but in runtime behavior.*

- **T2 – MPI 3.1 rollback**: Rebuilding the pipeline with MPI 3.1 (pre-upgrade version) eliminates failures on all trajectories, including large ones.  
  → *Proves that the MPI 4.1 runtime is a critical factor.*  
  → *Indicates that the new MPI version introduces a signal-handling bug.*

- **T3 – Unlimited stack ulimit**: Raising the stack size limit to unlimited (via `ulimit -s unlimited`) on two compute nodes eliminates failures for large trajectories (>4 GB).  
  → *Directly resolves the failure pattern.*  
  → *Confirms that stack overflow is a key component of the failure mechanism.*

- **T4 – strace capture**: A failing run shows a `SIGPIPE` delivered to a process attempting to write to a pipe whose read end is held by the scheduler’s resource tracker daemon.  
  → *Identifies the exact signal and its source: the pipe used for communication with the resource tracker.*  
  → *Explains exit code 141 (a SIGPIPE on write = exit code 141 in Linux).*

- **T5 – Filer cache ratio correlation**: Cache hit ratio drops sharply during evening hours, coinciding with the cluster-wide backup window.  
  → *Shows a strong temporal correlation between failure clustering and evening hours.*  
  → *But does not explain why failures occur only on large files or how the pipe mechanism is triggered.*

- **T6 – Exit-code frequency scan**: Confirmed that exit code 141 appears exclusively during RMSD-fit, never in other stages.  
  → *Validates that the failure occurs at a specific stage and under specific conditions.*

- **T7 – Evening-window job distribution**: Job failures are concentrated between 6:00–9:00 PM across all nodes.  
  → *Confirms temporal clustering; same as T5.*

## **Root Cause Determination**

The root cause is **a combination of the scheduler upgrade and the MPI 4.1 runtime’s signal handling behavior**, which leads to a **SIGPIPE** being delivered during memory-mapped trajectory processing in large files, under specific timing conditions.

### **Causal Chain (with evidence identifiers)**

1. **Scheduler version 21 introduced strict ulimit enforcement** (T5, T6) and now enforces process tracking via a pipe-based resource tracker daemon (CLUSTER CONTEXT).  
   → This is new behavior compared to version 19 or 20.

2. The **MPI 4.1 runtime**, when built against the patched interconnect driver, registers an `atexit()` handler that attempts to communicate with the scheduler’s resource tracker via a **pipe** (T4).  
   → In MPI 3.1, this communication used a Unix socket; in MPI 4.1, it uses a pipe.

3. During RMSD-fit processing of large trajectories (>4 GB), the software memory-maps the trajectory file and spawns one worker per replica.  
   → This creates a high-memory footprint and increases process lifetime, increasing the chance that the `atexit()` handler runs after the process group is terminated or during cleanup.

4. When the **resource tracker daemon** holds the read end of the pipe (as it does in version 21), any attempt by the MPI runtime to write to the pipe—such as during an `atexit()` call—results in a **SIGPIPE** being delivered to the process.  
   → This is confirmed via T4.

5. The **stack size limit of 8 MB per job (default)**, enforced by version 21, is insufficient for large trajectory memory mapping and worker initialization.  
   → This causes stack overflow during execution in MPI 4.1, especially when the process group is large or complex.  
   → T3 shows that raising the ulimit to unlimited resolves this.

6. **Large trajectories (>4 GB)** require more memory and longer runtime, increasing the likelihood of stack overflow and process lifetime extension—both conditions that allow the `atexit()` handler to execute after the scheduler has already terminated the process group (via pipe liveness enforcement).  
   → T1 shows single-node replay works; this proves it is not a data or hardware issue.

7. **Evening clustering** occurs because during those hours, the filer’s cache hit ratio drops sharply due to the cluster-wide backup window (T5 and T7).  
   → This causes increased I/O latency and memory pressure on compute nodes—**but this does NOT cause the SIGPIPE failure**.  
   → Instead, it **exacerbates the timing of process termination**, making it more likely that the `atexit()` handler runs *after* the scheduler has closed the pipe (T4).  

8. The **postdoc’s colleague claims evening clustering is the root cause**—but this contradicts T4 and T3:  
   - If evening were the root, then failures should occur on all jobs during that time regardless of trajectory size or MPI version.  
   - But T1 shows single-node replay works; T2 shows MPI 3.1 fixes it; T3 shows ulimit fix resolves it.  
   → The failure is **trajectory-size and MPI-version dependent**, not just temporal.

9. Therefore, the **evening clustering is a correlative symptom** (T5 and T7), not a root cause.  
   → It reflects increased process termination timing due to I/O pressure, which amplifies the *likelihood* of the SIGPIPE occurring during cleanup—but does not trigger it directly.

> ✅ **Conclusion**: The failure mechanism is driven by **MPI 4.1’s atexit handler writing to a pipe** that the scheduler has closed (due to ulimit enforcement), leading to a **SIGPIPE**, which results in exit code 141. This only occurs under three conditions:  
> - Large trajectory (>4 GB) → high memory usage, long runtime  
> - Evening hours → increased process termination timing due to I/O pressure  
> - MPI 4.1 with default stack size (8 MB) → stack overflow and atexit execution  

Thus, **the root cause is not the evening window**, but rather a **runtime interaction between MPI 4.1’s signal handling and the scheduler’s pipe-based resource tracking**—which is made worse by insufficient stack limits.

## **Remediation Plan**

### **Immediate Fix**
Set the stack size limit to unlimited in all job submission templates for this pipeline.

> ✅ This resolves the failure mechanism because it prevents stack overflow during memory-mapped trajectory processing, which allows the MPI runtime to avoid triggering the atexit handler under conditions that would otherwise lead to SIGPIPE.

#### **Rollout Steps**

1. Edit the group’s standard job submission template (e.g., `postprocess.sh` or `slurm-submit.yaml`) and insert:
   ```bash
   ulimit -s unlimited
   ```
2. Place this line at the very beginning of the script, before any MPI commands are invoked.
3. Submit a test job with a 5 GB trajectory to verify success (use T6 as validation).
4. Deploy the updated template across all compute nodes via cluster configuration management (e.g., Ansible or config repo).

> ⚠️ *This fix does not require changes to the scheduler, filer, or MPI version.*

### **Verification Protocol**

| Step | Description |
|------|-------------|

| **Queue-level verification** | Submit a job with a 5 GB trajectory; monitor logs for exit code 141. Should show zero failures. |
| **Weekly validation** | Run a full regression suite on a representative set of large trajectories (>4 GB) during evening hours. Confirm no new failures occur. |

> ✅ This verifies the fix works at all levels: node, job, and pipeline-wide.

---

### **Prevention Measures**

1. **Monitoring**: Add a monitoring alert for `exit code 141` in RMSD-fit stage with a threshold of ≥3 occurrences per hour.  
   → Trigger escalation if sustained over two hours.

2. **Ulimit policy**: Enforce stack size limits of at least 8 MB (or unlimited) for any job using memory-mapped trajectory processing, especially when running MPI-based post-processing.

3. **Change management**: Require all software upgrades (especially MPI or runtime libraries) to include a compatibility review with the scheduler and resource tracking components.  
   → Any new version must be tested in isolation against known failure patterns before deployment.

4. **Documentation**: Update the group’s runbook to explicitly state that large trajectory jobs require stack size limits raised for MPI-based post-processing.

---

### **Residual Risk Note**

This fix resolves the observed failures but does not address:

- The **underlying instability of the resource tracker daemon** when communicating with MPI processes via pipes.  
- Potential **performance degradation** in long-running, memory-intensive simulations due to increased process cleanup overhead (though this is currently unobserved).  

> 🔍 *Follow-up diagnostics needed*:  
> - Test whether the failure rate drops after the fix under high I/O load (e.g., during backup window)  
> - Monitor for any new SIGPIPE events in logs when MPI 4.1 runs with large files and no ulimit set  
> - Evaluate if a more robust communication mechanism (e.g., socket-based atexit) could replace the pipe  

> ❌ *This fix does not resolve the root issue of the scheduler’s resource tracking design, only its symptom under current conditions.*
