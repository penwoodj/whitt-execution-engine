a change summarizer, /tmp/opencode/diffsum. fixture: two versions of a 100-line config-ish document, v1 and v2, with a realistic change set between them: ~8 lines added, ~5 removed, ~6 modified, and some pure whitespace and comment churn that i don't want polluting the report, 4 such noise changes. the tool: compute the diff yourself or use difflib, either way classify each hunk as add, remove, modify, or noise, noise means whitespace-only or comment-only changes, classification rule stated. the deliverable: a change-summary.md written for a human, grouped by add/remove/modify with the actual content lines quoted, noise summarized in one sentence with a count, no lines dumped for it, and a stats table, adds, removes, modifies, noise. plus a machine copy changes.json. one honest-check: pick the two most important changes, your judgment, say why in one line each, i want to see the priority call, not just the inventory. keep v1 and v2 untouched, outputs only. standard library, deterministic, paste the stats table and your two important changes in chat at the end.

the summary is the deliverable, not the raw diff: counts first, added lines, removed, changed blocks, with changed defined as a delete-plus-add pair within a small window, definition stated. then the five biggest changes, each a one-line description with the hunk location, and the moved-block detection matters too, text deleted in one place and added in another is a move, not a change, and conflating them inflates the edit story. word-level stats supplement the line-level ones, since a one-word edit in a hundred-line paragraph is invisible to line diffs and that's exactly the edit that changes meaning. deterministic, rerun-stable, and paste the counts table plus the top-five changes in chat. and the whole thing reruns byte-identical, which for a diff summary is trivially achievable and therefore non-negotiable.
